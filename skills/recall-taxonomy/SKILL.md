# Recall taxonomy

Use the selected profile's installed Recall CLI. The connection's recall-bridge skill supplies its absolute launcher when `recall` is not on PATH. This skill requires `taxonomy` in that runtime's help; an older runtime needs an app update. Do not switch to a developer checkout, edit the database, or pretend a queued classification is applied.

Classify the content being created or organized. Routine learning capture alone does not authorize a taxonomy sweep. Keep existing note/card identities, content, review history and schedules. The app owns scoring; never set expertise, ratings, or evidence from assistant explanations or imported material.

1. Run `recall taxonomy list` and read its root policy. Read the relevant note/card content with the normal Knowledge/card tools. Search existing node labels, aliases, full ancestor paths and canonical card concept IDs before creating a branch. Titles and tags are search hints, not classifications: Apache Iceberg and iceberg orders belong to different concepts. Never promote every imported tag into a top-level domain.
2. Select a primary broader-to-specific path within the profile's approved domains. Reuse its nodes, or add only missing meaningful levels. For the approved three-domain organization, use **Computing** (`computing`), **Mathematics & Statistics** (`mathematics-statistics`), and **Economics & Finance** (`economics-finance`). Read [classification guidance](references/classification.md) for boundaries and mixed-content notes. Preserve a different profile's established policy; applying this three-domain policy to another profile requires an authorized organization change. Avoid forcing unrelated ideas into a fixed number of levels.
3. Map existing identities to the most specific appropriate node. Prefer a `concept` mapping for cards that share a canonical concept ID. A `card` mapping is only fallback placement for that whole canonical concept when no explicit concept mapping exists; it does not move one objective independently. Keep card-mapping targets consistent across its variants, or reconcile them with a single concept mapping. Map a KB note with both its source ID and canonical note ID. A node may have both note and practice mappings. Never create duplicate cards to improve graph coverage.
4. Keep cross-connections separate from parentage. Use a supporting source for `explicit` links already established in content. Label inferred connections `suggested`; do not turn a plausible prerequisite or analogy into a confirmed relationship. These edges do not multiply score contributions.
5. Prepare a scoped plan with the current `expectedRevision`. Run `recall taxonomy preview PLAN.json` and inspect its added, changed and removed records. Apply within the authorized creation/organization scope with `recall taxonomy apply PLAN.json --apply`. When queued, check `recall taxonomy status REQUEST_ID` for an applied receipt, then read the taxonomy to verify the paths and mappings. A revision conflict requires re-reading and reconciling; do not blindly replace the expected revision.

Read [the plan contract](references/plan.md) when constructing a plan. New cards must be imported and new notes indexed before their identities can be mapped. If creation succeeds but classification is pending or blocked, report the saved content and the separate classification status; retry the mapping rather than duplicating the content.

For an authorized whole-library pass, reconcile all configured source documents with the indexed inventory, inspect every included note/card's content, and retain a private identity-to-path inventory with reasons, uncertainties and unresolved records. Check missing/unreadable documents and duplicate identities before claiming complete coverage. Administrative indexes and setup guides are navigation, not learned concepts; preserve their identities and use a supported navigation placement instead of inventing subject matter. Reorganization changes taxonomy mappings, not note prose, card identities, ratings or schedules.

Use equal branch weights (`1`) by default. A deliberate weighting change needs a clear domain/assessment rationale and the user's requested organization scope. Card count, review frequency, difficulty labels, or desired score are not reasons to inflate a branch. Preserve existing weights when adding neighbors. Unreviewed is unassessed; suspending practice is not removal of a competency.
